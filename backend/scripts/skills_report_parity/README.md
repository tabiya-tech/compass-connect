# Skills report parity (frontend ⇄ backend)

The skills report (CV) is generated in two places, while we move the generation from the frontend to the backend:

| Format | Frontend (`frontend-new/src/experiences/report`) | Backend (`backend/app/skills_report`)                    |
|--------|--------------------------------------------------|----------------------------------------------------------|
| PDF    | `@react-pdf/renderer` 3.4                        | `reportlab` + a port of react-pdf's text/layout engine   |
| DOCX   | `docx` 8.5 (docx.js)                             | `python-docx`                                            |

This tool checks that, **given the same details, both generate the same documents**.

## What "the same" means

Two different PDF/DOCX libraries never produce byte-identical files (object order, font subsetting, compression,
zip timestamps, creation dates and ids). So each file is reduced to a **canonical model** of what a reader sees, and
the SHA-256 of that model is compared:

- **PDF** (`canonical_pdf.py`): page count and size; for every page, every text line in reading order as styled spans
  (text, font, size, colour) and the rendered size of every image. Additionally, the position of every line, image
  and border box is compared with a tolerance (default 0.5pt; in practice the deviation is ≤ 0.01pt).
- **DOCX** (`canonical_docx.py`): default and used styles, page setup, and the header, body and footer as paragraphs
  (style, alignment, spacing, keep-with-next, page-break-before, borders) with their runs (bold, italic, caps,
  colour, size, text, breaks, fields such as `PAGE`, and images as the SHA-256 of their bytes plus their size).

The raw SHA-256 of every file is also written to the report (`parity-report.json`) for reference.

## Running it

From `backend/`, with the backend venv activated and the frontend dependencies installed (`yarn install` in
`frontend-new`):

```bash
python scripts/skills_report_parity/run_parity.py                     # all fixtures
python scripts/skills_report_parity/run_parity.py -f 05_spanish_locale_accents
python scripts/skills_report_parity/run_parity.py --out-dir /tmp/parity  # keep the generated files
python scripts/skills_report_parity/run_parity.py --skip-frontend --out-dir /tmp/parity  # reuse frontend files
python scripts/skills_report_parity/run_parity.py --fixtures-dir /path/to/more/fixtures
```

Output:

```
fixture                               format frontend (canonical sha256) backend (canonical sha256) result
01_full_all_work_types                pdf    cb032ae1b14f1de1   cb032ae1b14f1de1   MATCH (3 pages, max deviation 0.0pt, layout ok)
01_full_all_work_types                docx   9c4045f5be290626   9c4045f5be290626   MATCH
...
ALL MATCH
```

On a mismatch, a unified diff of the canonical models is written to `<out-dir>/<fixture>/pdf.diff` / `docx.diff`.

The frontend files are generated by a Jest runner,
`frontend-new/src/experiences/report/_parity/generateParityReports.test.tsx`, which is skipped in normal test runs.
Each fixture is rendered with fresh module instances (like a fresh page load): react-pdf/fontkit keep caches across
renders that change the output of later reports (see "Known frontend issue" below).

## Fixtures

`fixtures/*.json` – one report per file:

```json
{
  "description": "what this fixture covers",
  "locale": "en-GB",
  "appName": "Compass",
  "config": { "...": "partial FRONTEND_SKILLS_REPORT_OUTPUT_CONFIG override" },
  "props": { "name": "...", "email": "...", "location": "...", "school": "...", "program": "...",
             "conversationConductedAt": "2025-03-14T09:30:00Z", "experiences": ["..."] }
}
```

They cover every work type, empty/minimal reports, config toggles and no logos, multiple logos, multi-page reports
(page splits, orphans/widows, `minPresenceAhead`), long words, new lines, other locales (es-ES, sw-KE), accented
skill sorting and special characters. Avoid `conversationConductedAt: null` (both sides would use "today").

## Golden hashes (backend CI without node)

`golden/<fixture>.json` holds the canonical hashes of the **frontend** documents. The backend unit test
`app/skills_report/test_service.py::TestParityWithFrontend` checks that the backend still produces them, so parity
regressions are caught by the backend CI. After changing the frontend report (or adding a fixture), regenerate them:

```bash
python scripts/skills_report_parity/run_parity.py --write-golden
```

## Keeping both implementations in sync

The backend mirrors the frontend components 1:1, a change in one must be made in the other:

| Frontend                                              | Backend                                   |
|-------------------------------------------------------|-------------------------------------------|
| `reportPdf/SkillReportPDF.tsx`, `components/**`, `styles.ts` | `app/skills_report/pdf/document.py` |
| `reportDocx/constructSkillReportDocument.ts`, `components/**` | `app/skills_report/docx/__init__.py` |
| `util.ts`, `reportContent.ts`, `config/*`             | `utils.py`, `content.py`, `types.py`      |
| `i18n/locales/*/translation.json` (`experiences.report`) | `app/i18n/locales/*/skills_report.json` |
| `public/*.png`, `public/*.svg`, `public/fonts/Inter-4.0` | `app/skills_report/assets/`              |

The PDF engine (`app/skills_report/pdf/text_kit.py`, `layout.py`, `hyphenation/`) is a port of the parts of
`@react-pdf/textkit` 4.4.1 and `@react-pdf/layout` 3.13 the report uses (Knuth & Plass line breaking with
`hyphen` en-us syllables, OpenType shaping with HarfBuzz instead of fontkit, react-pdf's justification of
overflowing lines, yoga-like flex layout incl. flex shrink, and react-pdf's pagination rules). Upgrading
`@react-pdf/renderer` in the frontend may require updating the port: run the parity check after any upgrade.

## Known frontend issue found by this tool

fontkit (used by react-pdf) caches glyph objects with the code points they were first created with, for the
lifetime of the page. After a report is generated, a later report in the same browser session can contain glyphs
without a ToUnicode mapping: the PDF looks right, but its text layer misses letters (e.g. "npaid Work" instead of
"Unpaid Work" when copying, searching, or parsing the CV with an ATS / screen reader). Reproduce by rendering an es-AR
report and then a sw-KE report in the same process. The backend does not have this issue.
